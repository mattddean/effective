# Effect compatibility and automatic releases

Researched 2026-11-09. Recommendation below is a design, not configured automation. Primary sources are linked inline; implementation-derived conclusions are identified explicitly.

## Recommendation

Use an exact support manifest, a small candidate/admission script, a complete GitHub Actions matrix, Changesets for versioning, and npm OIDC publishing. Renovate can discover and group candidate dependency updates, but must not own the published Effect support range. If detecting **every** intervening release matters, use a scheduled registry-enumeration script as the discovery authority. None of the release tools supplies the compatibility/admission policy.

Current repository observations: `package.json` admits `effect: ~4.1.2` but pins development Effect and two companions to `4.1.2`. CI runs one locked installation. `scripts/check-package.mjs` explicitly installs `manifest.devDependencies.effect` in its temporary consumer. The tag-driven publishing workflow repeats those checks but has no compatibility matrix. Thus the present checks do not establish compatibility with every admitted Effect version. These are local-file observations, not registry-version claims.

## Supported versions and genuine matrix tests

Maintain one canonical list of admitted exact stable versions, with companion-package pins per test row. Generate `peerDependencies.effect` as the sorted exact disjunction, for example `4.1.2 || 4.1.3` **only after both versions pass**. This example does not claim `4.1.3` exists or works. Validate the peer string structurally: each alternative must be a full exact version, with no caret, tilde, wildcard, inequality, or partial version, and its set must equal the manifest. SemVer's OR syntax supports this; a tilde admits future patches, so testing today's available patches cannot establish the stated invariant. [npm's SemVer implementation](https://github.com/npm/node-semver#ranges)

Custom test requirements:

- Derive the matrix from the base branch's entire support set plus candidates. Reject deletions or omitted old rows; do not let a candidate PR silently shrink its own test obligation. Run the complete matrix on ordinary library changes too.
- In each clean job, install the row's exact Effect **and companion tuple**, then type-check, execute unit/integration contracts, and build. An unmodified `npm ci` restores the development pin. Prefer generating a disposable checkout manifest/lockfile for the selected tuple; keep production files untouched. Do not use peer-conflict suppression to make an invalid tuple install.
- Build the eventual release artifact once against the chosen development baseline, then test that **same tarball** in isolated consumers for every row. Rebuilding separately against each Effect version is useful source testing but does not prove that one published artifact works everywhere.
- Pass the selected Effect version explicitly into `check-package.mjs`; remove its hard-coded development-pin fallback in compatibility CI. Each fresh consumer must install the tarball and `effect@<row-version>` together, without a copied repository lockfile or workspace links. Assert the actually resolved version, inspect `npm ls effect --all` for unexpected copies, compile declarations/examples, and exercise root and storage imports plus representative behavior. Test optional storage both absent and installed. Exact package specifications and tarball installs are supported npm operations; fixture setup and assertions are custom. [npm install](https://docs.npmjs.com/cli/v11/commands/npm-install/)

GitHub provides dynamic matrices and job dependencies; use `fail-fast: false`, no `continue-on-error`, and a stable required aggregate check that explicitly fails on failed, cancelled, skipped, empty, or missing required results. Publishing must depend on successful validation at the release commit, rather than on an unrelated green workflow. [Matrices](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/run-job-variations), [job dependencies](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-jobs)

## What Renovate does and does not supply

- npm `auto` widens peers; explicit `rangeStrategy: "widen"` preserves range-style compatibility, e.g. caret alternatives. It is not a tested-version ledger. `allowedVersions` filters proposed updates; it does not constrain the published peer range or prove compatibility. An exact allowlist would also prevent discovering versions outside it. Use it for candidate policy, e.g. a chosen major, not admission. It cannot share a package rule with `matchUpdateTypes`.
- `postUpgradeTasks` can invoke custom generators before committing, but require administrator command permissions; hosted availability depends on plan. Do not assume a repository setting alone enables them. A separate bot workflow is a portable alternative.

Sources: [range strategies](https://docs.renovatebot.com/configuration-options/#rangestrategy), [allowedVersions](https://docs.renovatebot.com/configuration-options/#allowedversions), [post-upgrade tasks](https://docs.renovatebot.com/configuration-options/#postupgradetasks), [administrator command allowlist](https://docs.renovatebot.com/self-hosted-configuration/#allowedcommands).

**Exact-version edge cases:** inspected Renovate `getNewValue` returns the new version immediately for a single bare exact version, before its `widen` branch. Thus bare `4.1.2` does not bootstrap an append-only list. Explicit `=version` alternatives take a different path; bare disjunctions also enter complex-range parsing. Conclusion from source inspection: do not promise arbitrary exact disjunction preservation without fixtures against the deployed Renovate version. Generate and validate the peer list yourself. [Renovate npm range implementation](https://github.com/renovatebot/renovate/blob/main/lib/modules/versioning/npm/range.ts)

Renovate provides `group:effectMonorepo`; alternatively match the repository's actual packages (`effect`, `@effect/platform-bun`, `@effect/sql-sqlite-bun`) under one `groupName`. Grouping combines updates into a PR; it does **not** select a proven compatible tuple or imply identical version numbers. Read each companion's published peer requirements and pin a valid tuple per admitted Effect version; latest companions may reject older supported Effect versions. [Effect grouping preset](https://docs.renovatebot.com/presets-group/#groupeffectmonorepo)

Renovate supports PR automerge after required checks. Configure actual branch protection/rulesets with the stable compatibility check and an up-to-date merge base or merge queue; disable privileged bypass. If using a merge queue, run the checks on `merge_group`. `automerge: true` alone is insufficient protection. Reviews required by policy can intentionally prevent unattended merging. [Renovate automerge](https://docs.renovatebot.com/key-concepts/automerge/), [GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

## Release-tool choice

| Tool | Built in | Required glue / limitation |
| --- | --- | --- |
| **Changesets action — recommended** | Consumes changeset files, creates/updates version-and-changelog PRs, runs a configured publishing command. | Candidate bot writes an idempotent patch changeset for additive support; a separate policy automerges the release PR after checks. Action does not infer a release from a peer edit or test compatibility. |
| **release-please** | Conventional Commit analysis, version/changelog release PR, tags and GitHub releases. | Supply release-worthy compatibility commit messages; npm publish is a separate conditional step/job. Release PR also needs automatic merging and checks. |
| **semantic-release** | Commit analysis, version selection, release notes, npm/GitHub publishing through plugins, without a release PR. | Gate execution with the complete matrix. Ordinary `chore(deps)` does not release by default; use an explicit compatibility rule or a release-worthy commit type. Best alternative if eliminating the second PR matters more than keeping version changes reviewable. |

Sources: [Changesets action](https://github.com/changesets/action), [release-please action, including npm example](https://github.com/googleapis/release-please-action), [semantic-release CI contract](https://semantic-release.org/usage/ci-configuration/), [commit-analyzer rules](https://github.com/semantic-release/commit-analyzer), [semantic-release npm plugin](https://github.com/semantic-release/npm).

Version caveat: Changesets action `main` currently documents development v2/CLI v3, split version/pack/publish sub-actions, and renamed inputs (`publish-script`, `github-token`). Maintenance v1/CLI v2 uses `publish` and `GITHUB_TOKEN`. Pin a reviewed compatible released pair; do not mix examples. Prefer separate versioning and publishing permissions. [Current action README](https://github.com/changesets/action), [v1 README](https://github.com/changesets/action/blob/maintenance/v1/README.md)

Automation identity matters: current GitHub docs say `GITHUB_TOKEN`-created/updated PRs can produce approval-required CI runs; token-generated pushes/tags generally do not trigger further workflows. Use a narrowly scoped GitHub App installation token for unattended candidate/release PRs. For release publication, prefer a direct gated job over relying on a token-created tag to start this repo's existing publishing workflow. This current GitHub behavior is more nuanced than release-please's older blanket warning. [GitHub workflow triggering rules](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow)

## Concrete end-to-end architecture

1. **Discover:** scheduled trusted script queries `npm view effect versions --json`, filters stable versions by an explicit major policy, and subtracts admitted and already-pending candidates. Keep failure records with source SHA so unchanged failures do not churn but can be retried after fixes. Enumerate registry versions rather than interpreting `latest` as a release history. Renovate grouped updates can be the trigger instead if skipped intermediate versions need not be supported. [npm view](https://docs.npmjs.com/cli/v11/commands/npm-view/)
2. **Prove candidates:** open/update a candidate PR containing exact candidate/companion metadata. Test every existing supported row plus the candidate. Do not change published support metadata on the default branch yet. Failed candidates stay unsupported.
3. **Prepare admission:** only after success at the candidate SHA, the bot appends exact supported rows, generates the peer disjunction and patch changeset, and refreshes any development pins/lockfile. Run the full checks again on that final PR SHA; merge only when green. The extra run prevents a bot's metadata edit from inheriting stale approval. Admit no untested intermediate/future versions.
4. **Version:** Changesets creates the release PR; the App enables automerge under the same required checks. Adding support without removing existing support is a project-defined patch policy; dropping support or changing API requires deliberate version policy and review.
5. **Validate release:** after release PR merge, serialize release runs, select that exact commit, validate manifest/peer/version agreement, build/pack, and test the final tarball across the entire admitted set. Publish that tested tarball only after the aggregate succeeds. Do not let a publish lifecycle rebuild replace the validated bytes.
6. **Publish and reconcile:** use a dedicated OIDC job; confirm npm's resulting version/metadata and record the Git tag/release. On retries, check whether the exact version already exists; never overwrite it or silently skip a mismatch. Registry publication and GitHub tagging are not an atomic transaction. [npm publish](https://docs.npmjs.com/cli/v11/commands/npm-publish/)

Steps 1–3, manifest generation/validation, consumer fixtures, result aggregation, release-PR automerge policy, and reconciliation are **custom script/workflow glue**. Changesets handles version/changelog mechanics; npm handles publishing authentication. No tool certifies complete behavioral compatibility: tests establish the chosen contract only, and matrix cost grows with the admitted set. Test companion tuples explicitly; they do not establish every possible cross-product of companion versions.

## npm trusted publishing prerequisites

Use a GitHub-hosted runner, Node >=22.14.0, npm >=11.5.1, and job permission `id-token: write`; no npm publishing token is needed. Configure npm trust for the exact owner/repository/workflow filename and environment (`npm` here, if retained). Explicitly permit direct `npm publish`: newly created publishers default to allowing staging. Unattended publication cannot depend on a manual environment/staging approval. GitHub OIDC automatically adds provenance for public repositories publishing public packages. [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/)

Bootstrap is separate: npm trust configuration requires an existing package and appropriate account access/2FA. Confirm initial publication and trust outside the automated compatibility loop. Existing account permissions, registry package state, environment approval rules, and repository protection settings were not verified here. [npm trust prerequisites](https://docs.npmjs.com/cli/v11/commands/npm-trust/)
